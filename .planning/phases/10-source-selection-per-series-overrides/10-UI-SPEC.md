## Field Contracts

### Field 1 — Source Language Preference

**What it is:** An ordered list of 2-letter ISO-639-1 language codes. Corresponds to `series.source_lang_override` (JSON list | NULL). Empty list is treated identically to NULL (both mean "inherit global").

**Input control:** `SourcePriorityEditor` — a horizontal chip list with add/remove.

Chip anatomy (each language code in the list):
- Background: `#1e293b` (same as inference-badge bg — visually grouped, not accent)
- Text: `text-text-primary` (12px)
- Remove button: `×` in `text-text-muted`, hover `text-[#f87171]` (destructive red), aria-label `"Remove {code} from source priority"`
- Chip height: 28px (`h-7`)
- Chip horizontal padding: 8px (`px-2`)
- Gap between chips: 8px (`gap-2`)

"Add language" control:
- A plain `<input type="text">` styled as `h-7 w-16 bg-bg-surface border border-[#2d3148] rounded px-2 text-xs text-text-primary` with placeholder `"+ Add"`.
- On Enter or blur with non-empty value: validate the code is 2 letters a-z. If invalid, show inline error text (12px, `text-[#f87171]`): `"Must be a 2-letter ISO-639-1 code (e.g. ko, zh, en)"`. If valid and not already in the list, append to end; clear input. Duplicate codes are silently ignored (no error).

"Clear source override" link:
- Rendered only when `source_lang_override` is non-null and non-empty (i.e. an actual override is set).
- `<button type="button" className="text-xs text-accent">Clear source override</button>`
- Sets `source_lang_override` to `null` (inherit global), submits immediately via `PATCH /api/bible/series/{id}/overrides`.

Provenance badge (inline, below the field label):
- **Inherited:** `<span className="text-xs text-text-muted">Inherited from global config: {globalDefault.join(", ")}</span>`
- **Overridden:** `<span className="text-xs text-accent">Per-series override active</span>`

Global default display: show the global `source_lang_priority` list from settings in the "inherited" badge text. Read from the `/api/settings` response at page load (already loaded by `Settings.tsx` pattern — load independently in `OverridesSection` via a `useEffect` + `getSettings()` call). On load error, show `"inherited from global config"` without the value.

### Field 2 — Model Override

**What it is:** A free-text model ID string. Corresponds to `series.model_override` (str | NULL). Empty string is treated as NULL by the save handler (cleared override → inherit global).

**Input control:** `TextField` component (already exists in `BibleEditor.tsx`):
- `id="model_override"`
- `label="Model override"`
- `placeholder={globalModel || "e.g. gpt-4o"}` — show the global `llm_model` as placeholder so the user can see what they'd be overriding.
- `value={modelValue}` — empty string when no override.

"Clear model override" link: same pattern as source language — rendered only when the field is non-empty; sets to `""` (which the save handler converts to `null`).

Provenance badge:
- **Inherited:** `<span className="text-xs text-text-muted">Inherited: {globalModel}</span>`
- **Overridden:** `<span className="text-xs text-accent">Per-series override active</span>`

Validation: no format validation on model ID — it is a free-text field (model IDs are endpoint-dependent and unknowable at the UI layer). Length limit: 256 characters, enforced client-side only (silently truncate or show inline `text-[#f87171]` error: `"Model ID must be 256 characters or fewer"`).

### Field 3 — Register

**What it is:** The series register field, already fully implemented in the "Register" tab. The Overrides section surfaces it alongside the other two overrides so the operator can manage all three in one place.

**Implementation:** Inline reduced version of `RegisterSection` — NOT a full tab duplication. Render:
1. The `TextField` (id `"register_override"`, label `"Register"`, placeholder `"e.g. formal, intimate, historical"`).
2. `LockBadge` + `LockToggleButton` side-by-side (reuse exact pattern from `RegisterSection`).
3. Advisory strip if unlocked (same `#1e3a5f` / `#60a5fa` strip: `"This value may be overwritten on the next episode analysis. Lock to pin it."`).
4. Register is saved/locked via the EXISTING `PATCH /api/bible/series/{id}/register` endpoint (not `/overrides`). The Overrides section calls `patchRegister()` from `api/client.ts` — the same function the Register tab uses.

Register "Save" is included in the single "Save Overrides" button only for the text fields (source + model). Register changes go through the existing `patchRegister` function independently (consistent with Phase-8 behavior — register has its own save pathway). The save button in the Overrides section does NOT touch register. Register dirty-state and save remain the same as in the Register tab.

## Interaction Contracts

### Save Flow (source_lang_override + model_override)

1. User modifies source priority list or model field → local state updates; "Save Overrides" button becomes enabled.
2. User clicks "Save Overrides":
   - Button shows `"Saving…"`, `disabled={true}`.
   - Call `patchSeriesOverrides(seriesId, { source_lang_override, model_override })`.
   - `source_lang_override`: send `null` if list is empty or was cleared; send the list otherwise.
   - `model_override`: send `null` if empty string; send the trimmed string otherwise.
3. On success:
   - `setBible()` to update the in-memory bible with the returned DTO.
   - `showToast({ message: "Overrides saved.", variant: "success" })`.
   - Button returns to enabled (dirty = false).
4. On error:
   - `showToast({ message: "Failed to save overrides. Check the server logs.", variant: "error" })`.
   - Button returns to enabled (dirty = true — user can retry).

"Clear override" links: fire their own immediate `patchSeriesOverrides` call without going through the Save button. They are always enabled (not gated on dirty state of other fields).

### Register Save (within Overrides section)

Follows identical flow to `RegisterSection.handleSave` / `toggleLock` — calls `patchRegister`. Success: `showToast({ message: "Register saved.", variant: "success" })`.

### Tab Switch

Switching to the Overrides tab does NOT auto-save pending changes in other tabs. Switching away from Overrides tab does NOT discard pending changes (standard React state lifecycle — state lives in `OverridesSection`, unmounted on tab switch). This is consistent with existing tab behavior in `BibleEditor`.

### Provenance Badge Updates

Provenance badges are derived from the current in-memory `bible` state (after load or after a successful save). They do not poll; they reflect the last confirmed server state.

## API Contract (frontend perspective)

### New client wrapper to add to `api/client.ts`

```typescript
export interface SeriesOverridesRequest {
  source_lang_override: string[] | null;  // null = clear / inherit global
  model_override: string | null;          // null = clear / inherit global
}

// DTO additions — extend SeriesBibleDTO and SeriesListItem with:
//   source_lang_override: string[] | null
//   model_override: string | null

/** PATCH /api/bible/series/{id}/overrides — set source-priority and model overrides. */
export async function patchSeriesOverrides(
  seriesId: number,
  payload: SeriesOverridesRequest,
): Promise<SeriesBibleDTO> {
  const resp = await fetchWithTimeout(`/api/bible/series/${seriesId}/overrides`, {
    method: "PATCH",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(payload),
  });
  if (!resp.ok) throw new Error(`PATCH overrides: ${resp.status}`);
  return resp.json();
}
```

Note: `patchRegister` is already in `client.ts` and used unchanged.

HTTP error mapping:
- `422 Unprocessable Entity` — invalid `source_lang_override` value (non-array, non-string elements). Treat as generic save error. Toast: `"Failed to save overrides. Check the server logs."`.
- `404 Not Found` — series not found. Toast: `"Series not found."`.
- Network error / timeout — Toast: `"Failed to save overrides. Check the server logs."`.

## Implementation Notes

1. **Tab addition:** The tab array in `BibleEditor` is a static `[Tab, string][]` literal. Add `["overrides", "Overrides"]` to the tuple list and add `Tab = "characters" | "address_map" | "terms" | "register" | "overrides"` to the union type.

2. **OverridesSection receives:** `seriesId: number`, `bible: SeriesBibleDTO`, `setBible: React.Dispatch<...>`, `showToast: (t: ...) => void`. Same props signature as all other section components.

3. **SeriesBibleDTO extension:** Add `source_lang_override: string[] | null` and `model_override: string | null` to the `SeriesBibleDTO` interface in `client.ts`. These fields come from the existing `/api/series/{id}/bible` response once the backend migration (0003) ships.

4. **Global settings load:** `OverridesSection` calls `getSettings()` in a `useEffect` on mount to populate the provenance badge values. On error, degrade gracefully (show "Inherited from global config" without the specific value). This is a secondary load — failure must not block the section from rendering.

5. **Register sub-section wiring:** The register sub-section inside `OverridesSection` manages its own `registerValue` state initialized from `bible.register`. It calls `patchRegister(seriesId, ...)` directly — the same `patchRegister` from `client.ts` the Register tab uses. `setBible` is called on success to keep the in-memory bible consistent.

6. **Source priority list ordering:** The list order is the override priority order — first item is most preferred. The `SourcePriorityEditor` renders items in list order. Reordering is out of scope for Phase 10 (the user adds/removes, and the order is append-to-end). If drag-to-reorder is desired, it is a deferred nicety.

7. **No shadcn, no new design tokens:** This spec introduces zero new tokens. All visual values are already declared in `tailwind.config.js` and used in existing components.
